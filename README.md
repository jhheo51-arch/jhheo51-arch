# 허재혁 | Salesforce MC 및 CRM 기획

**왜 이 고객에게, 왜 지금, 왜 이 방식인가.**

고객에게 닿는 결정은, 실행 전에 설명돼야 합니다.

웹 문의가 Lead로 남는지 확인한 회사 경험에서 출발해, 개인 프로젝트에서 캠페인 대상과 비교 기준을 설계하고 Salesforce에서 안전 VOC 이관 규칙을 구현했습니다. 실제 업무, 공개 데이터 분석, 가상 구현과 합성 실습을 구분해 기록합니다.

## 대표 사례

1. **Lead에서 재방문 캠페인까지.** 위플래너에서 시험 Lead 생성 PoC를 확인했습니다. 별도 개인 프로젝트 [CRM LOOP](https://github.com/jhheo51-arch/crm-loop)에서는 공개 거래 자료로 대상 후보 666명을 고르고 미발송 비교군을 설계했습니다. [회사 경험의 공개 화면은 PM 포트폴리오 10쪽](./허재혁_포트폴리오_PM.pdf)에 있습니다. 실제 발송과 후속 영업 성과는 확인되지 않았습니다.
2. **안전 VOC의 이관 기준.** [Aurora Owners 360](https://github.com/jhheo51-arch/aurora-owners-360)에서 가상 전기차 고객센터의 차주, 차량, 보증 기록과 이관 규칙을 Salesforce Developer Edition에 구현했습니다. 2시간은 설정 기한이며 실제 처리 성과가 아닙니다.
3. **CRM A/B의 적용 판단.** [선택적 정기 점검 안내의 합성 실습](./portfolio/salesforce-mc-crm/service_revisit_demo/)에서 방문 완료와 고객 보호 지표를 함께 보고 전면 적용을 보류했습니다. 전자책은 비공개 검토 중이고 도구는 제작 중입니다.

## 일하는 방식

1. 누가 어느 접점에서 멈추는지와 다음 행동을 먼저 정합니다.
2. 대상, 제외 조건, 비교 기준과 판단을 바꿀 수 있는 근거를 함께 적습니다.
3. 기획을 화면, 규칙과 계산 코드로 옮겨 입력을 바꿔 검사합니다.
4. 검사 통과, 가상 자료의 계산과 실제 고객 효과를 별개의 결과로 기록합니다.

코드 작성과 조사, 검사를 보조하는 도구로 Codex와 Claude Code를 사용합니다. 문제와 기능 범위, 최종 판단은 제가 정하고 결과를 검토합니다. 가상 고객과 시제품의 결과를 실제 회사의 운영 성과로 제시하지 않습니다.
