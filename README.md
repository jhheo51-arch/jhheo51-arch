# 허재혁

**Salesforce Marketing Cloud / CRM / A/B Testing**

## 왜 이 고객에게, 왜 지금, 왜 이 방식인가.

고객에게 닿는 결정은, 실행 전에 설명돼야 합니다.

저는 고객 기록을 모으는 데서 멈추지 않고 **대상 선정, 안전 이관, 실험 후 적용 판단**까지 연결해 봅니다. 아래 세 사례에는 제가 정한 기준과 그 기준을 검토할 수 있는 자료를 함께 두었습니다.

---

### 01 / 왜 이 고객에게? — Lead와 캠페인 대상

위플래너에서 웹 문의가 Lead로 생성되는 **시험 PoC**를 확인했습니다. 이후 별도 개인 프로젝트 [CRM LOOP](https://github.com/jhheo51-arch/crm-loop)에서 공개 거래 자료를 분석해 재방문 캠페인 대상 후보 **666명**을 선정하고 미발송 비교군을 설계했습니다. [회사 경험의 공개 화면은 PM 포트폴리오 10쪽](./허재혁_포트폴리오_PM.pdf)에 있습니다. 실제 캠페인 발송과 후속 영업 성과는 확인되지 않았습니다.

### 02 / 왜 지금? — 안전 VOC 이관

[Aurora Owners 360](https://github.com/jhheo51-arch/aurora-owners-360)에서 가상 전기차 고객센터의 차주, 차량, 보증 기록을 연결하고 안전 VOC를 담당자에게 넘기는 규칙을 **Salesforce Developer Edition**에 구현했습니다. **2시간**은 이관을 확인하기 위해 설정한 기한이며, 실제 처리 성과가 아닙니다.

### 03 / 왜 이 방식인가? — CRM A/B 적용 판단

[정기 점검 재방문 A/B 합성 실습](./portfolio/salesforce-mc-crm/service_revisit_demo/)에서 안내 문안 두 가지와 미발송 비교군을 설계했습니다. 가상 고객 **90,000명**으로 만든 자료에서 B의 28일 방문 완료율은 A보다 **1.09%p** 높았지만, 고객 보호 지표와 서비스센터 수용량을 확인할 수 없어 **전면 적용을 보류**했습니다. 실제 고객에게 발송하거나 Salesforce MC에서 운영한 결과는 아닙니다.

A/B 테스트 방법론을 전자책으로 정리하고 판단 도구로 옮기는 작업은 계속 진행 중입니다. 전자책은 비공개 검토 중이며 도구는 제작 중입니다.

## 제가 일하는 순서

**문제 정의.** 누가 어느 접점에서 멈추는지와 다음 행동을 먼저 정합니다.

**기준 설계.** 대상과 제외 조건, 비교군, 중단 조건을 결과보다 먼저 적습니다.

**구현과 검사.** 화면, Salesforce 규칙, 계산 코드로 옮겨 입력을 바꿔 확인합니다.

**결과 기록.** 시험 PoC, 가상 구현, 합성 실습과 실제 고객 성과를 구분합니다.

코드 작성과 조사, 검사를 보조하는 도구로 Codex와 Claude Code를 사용합니다. 문제와 기능 범위, 최종 판단은 제가 정하고 결과를 검토합니다.
