고객군 분석과 캠페인 설계

프로젝트 저장소 ↗↓

회사 PoC에서 시작한 질문 · 공개 데이터 기반 개인 설계

연락할 고객을 고르기 전에, 보내지 않을 고객도 정했습니다.

캠페인 설계
UCI 공개 거래 데이터에서 2011년 12월 1일 기준 이탈 위험 고객 666명을 설계 대상으로 선정했습니다. 실제 발송은 없었습니다.
효과 분석
별도의 Hillstrom 공개 이메일 실험 64,000명을 분석해 발송군과 미발송군을 비교하는 방법을 검토했습니다.

출발점 / Lead 레코드 생성 PoC

화면의 완료 다음에, 레코드가 남는지.

웹 문의 입력 항목과 개인정보 동의값을 정리하고 Web-to-Lead로 보낼 값을 Lead 필드에 대응시켰습니다. 시험 문의를 제출한 뒤 Lead 목록과 상세 화면에서 레코드 생성과 저장값을 확인했습니다.

대상 선정 / UCI 구매 데이터

구매가 뜸해졌지만, 돌아올 가능성이 남은 고객부터.

구매 시점과 빈도로 고객군을 나누고, 이탈 위험 고객을 첫 시험 대상으로 골랐습니다.

5,812명분석 고객
666명캠페인 설계 대상
90일계획한 재구매 관측 기간

효과 측정 / 별도의 Hillstrom 공개 실험

방문을 늘리는 메일과, 이익을 남기는 발송은 다릅니다.

고객군별 효과와 발송 비용을 함께 보고, 전원 발송을 당연한 답으로 두지 않았습니다.

실행 설계 / MC Journey 설정안

비교할 고객을 남기고, 보호할 고객은 제외합니다.

동의·제외 조건 확인→발송 70% · 미발송 30%→두 군 모두 90일 재구매 관측

최근 14일 구매, 수신거부, 접촉 상한을 확인합니다. 첫 메시지는 쿠폰 없이, 구매한 고객은 남은 메일을 중지하도록 설계했습니다.

프로젝트 Q&A

Lead 레코드 생성 PoC에서 어디까지 확인했나요?

위플래너 인턴십에서 랜딩페이지 입력 항목과 개인정보 동의 화면을 정리하고 Web-to-Lead로 보낼 값을 Lead 필드에 대응시켰습니다. 시험 문의를 제출한 뒤 Lead 목록과 상세 화면에서 레코드와 입력값을 확인했습니다. 공개 PM 포트폴리오에 입력, 목록, 상세의 3개 화면이 남아 있습니다.

전체 매핑표, 실패·중복 처리, 실제 전환율과 후속 영업 성과는 확인 범위에 포함하지 않습니다. MC 연동 실적도 아닙니다. CRM LOOP에는 위플래너 고객 데이터나 성과를 사용하지 않았습니다.

기존 PM 포트폴리오 ↗
공개 실험은 어떻게 해석하고 발송 조건을 정했나요?

별도의 Hillstrom 이메일 무작위 실험 64,000명 분석에서 남성 상품 안내은 미발송군 대비 방문율 +7.66%p, 구매율 +0.68%p였습니다. UCI의 666명 분석이나 실제 MC 성과와 구분합니다. 작은 효과를 보기 위해 같은 설계의 6회차를 모으는 계획을 세웠습니다.

고객은 한 번만 진입하고 메시지는 최대 3통, 전체 마케팅 메일은 7일에 2통을 상한으로 뒀습니다. 동의에는 목적·채널·동의 시각·정책 버전 4개 항목을 요구했습니다. 666명은 동의와 제외 조건을 적용하기 전의 설계 대상이며 실제 발송 가능 수는 별도 확인이 필요합니다.

사람과 AI의 경계

규칙은 Flow가 검사하고, AI는 확인된 기록을 요약합니다.

AI에 Case 종결·보상 승인·유형 변경 권한을 주지 않았습니다.

개발 org 검증과 실제 적용의 차이는 무엇인가요?

PRD의 2026.10.14 수용 테스트에는 T3·T4·T8 기대값과 CLI 조회 결과가 기록돼 있습니다. T4의 설정 기한은 생성 +2.00시간이었습니다. 마지막 검증 배포 기록은 구성 요소 442/442개, Apex 테스트 82/82개 통과, 코드 커버리지 91.8%입니다.

이는 개발 org의 소스와 대표 경로 검증입니다. 실제 상담 해결률, 응답시간 단축, 2시간 내 첫 응답 달성률을 측정한 결과가 아닙니다. 실제 적용 시 직원별 권한, 새 org 설치, 접수와 첫 응답 시각을 확인해야 합니다. VOC-C 보상 시연의 450,000원은 VOC-T4의 안전 문제 해결 성과와 합치지 않습니다.

개발 org는 표준 객체 4개와 커스텀 객체 14개로 확장됐습니다. 객체 수 자체를 고객 효과로 해석하지 않습니다.

CRM A/B Test

실험의 결과와 적용 판단

↓

AI 협업 · 교육용 합성 실습

방문 완료율이 높아도 전면 적용을 보류했습니다.

합성 실습에서 예약 편의안의 28일 방문 완료율은 차량 관리 필요성 안내보다 1.09%p 높았습니다. 다만 개선 구간 하한은 최소 기준보다 낮았고, 수신 철회가 허용 범위를 넘을 위험도 배제할 수 없었습니다. 센터 수용량과 비용도 확인되지 않았습니다.

차이는 보였지만, 확인할 조건이 남았습니다.

충분히 큰 개선인가개선 구간 하한이 교육용 최소 기준보다 낮았습니다.

고객에게 괜찮은가수신 철회가 허용 범위를 넘게 악화될 위험을 배제하지 못했습니다.

현장에서 가능한가센터 수용량과 비용을 확인할 자료가 없었습니다.

전면 적용을 보류하고, 추가 확인 후 제한적 적용 여부를 재검토하기로 했습니다.

프로젝트 Q&A

실험 대상·관측 기간·판정 기준은 어떻게 정했나요?

마케팅 동의, 30일 내 점검 시기, 기존 예약 없음, 필수 안전 고지 대상 아님이라는 조건을 적용했습니다. 배정 뒤 예약·열람 여부와 관계없이 처음 배정된 군 전체를 분모에 남겼습니다. 안전 고지와 법적 의무 안내는 모든 군에서 별도로 처리해야 합니다. H는 동의 범위와 법적 의무를 확인한 경우에만 제한적으로 운영하는 조건입니다.

가상 시작 28일째 배정 45,069명 중 각자 28일을 채운 고객은 1,483명뿐이어서 중간 화면으로 최종 판정하지 않았습니다. 최종 완료 인원은 A 1,416명, B 1,597명, H 951명입니다. 사전 세 완료 비교를 고려한 보정 p값은 0.00352입니다.

B−A 수신 철회 차이의 탐색 구간은 [−0.15, +0.26]%p입니다. 최소 개선 +0.5%p와 허용 악화 +0.2%p는 합성 자료 생성 전에 정한 교육용 예시값입니다. 실제 기준은 사업 가치, 고객 보호, 운영 자료로 합의해야 합니다. 제한적 적용을 승인한 결과도 아닙니다.

합성 계획, 고객별 가상 원장, 코드, 계산 결과로 집계를 재현할 수 있습니다.

합성 실습 재현 방법 ↗계산 결과 ↗
A/B 전자책과 분석 도구는 어디까지 진행했나요?

정보통신 소대장 시절 대안 구성과 경로를 시험하고 실패 원인을 기록했습니다. 통제군·무작위 배정을 갖춘 정식 A/B는 아니었습니다. 이 경험을 CRM의 동의·배정·행동 지표·관측 기간이라는 언어로 다시 정의하기 위해 전자책을 쓰고 있습니다.

현재 v0.10, 90쪽 저자 검토본으로 공개 전입니다. 초기 76쪽 원고에서 진단 카드 60쪽을 참조편으로 분리하고 6개 완결 사례를 본문에 넣었습니다. 90쪽은 제작 분량이며 학습 효과가 아닙니다. 외부 통계·CRM 실무 검토와 독자 시험은 남아 있습니다.

TRI-V는 새로운 통계 원리가 아닌 저자 제안 정리 틀입니다. 분석 도구는 설계 중이며 완성된 SaaS가 아닙니다. 위 정기 점검 재방문 실습은 전자책에 실린 사례가 아닌 별도 AI 협업 합성 실습입니다.

Not Sent 진단과 후속 조치 기준을 설계했습니다.

발송 대상보다 실제 발송 건수가 적을 때, 어떤 미발송을 그대로 두고 어떤 건을 다시 확인해야 할까요? Salesforce 공식 안내를 참고해 수신거부 등 보호 제외는 유지하고 주소와 콘텐츠 오류는 다시 확인하는 미발송 진단 기준을 설계했습니다. 별도 가상 CSV 예시는 8행 중 같은 발송에 해당하는 7행의 분류를 보여 줍니다. 실제 Marketing Cloud 계정에서 추출하거나 발송한 기록은 없습니다.

먼저 확인할 것 같은 발송의 고객 키와 미발송 사유를 먼저 대조합니다. 수신거부에 따른 제외는 유지하고, 주소나 콘텐츠 오류는 수정 필요 여부를 확인합니다.

미발송 사유별 판단 기준

같은 발송 ID의 행을 골라 사유를 확인합니다.

  • 제외 유지수신거부와 보호 정책에 따른 제외는 그대로 둡니다.
  • 오류 확인주소와 콘텐츠를 점검한 뒤 발송 자격을 다시 확인합니다.
  • 판단 보류처음 보는 사유는 담당자가 확인할 때까지 보류합니다.

프로젝트 Q&A

열람률 대신 어떤 지표로 승자를 판단했나요?

제목·발송 시점·개인화를 구분하고, Apple MPP로 Open이 부풀 수 있음을 반영했습니다. Click과 사람의 검토를 승자 판단에 넣고, 예약·방문이 수집되지 않으면 행동 성과로 쓰지 않습니다.

Salesforce 지표 안내 ↗
Not Sent는 원인별로 어떻게 처리했나요?

SubscriberKey와 Reason을 기준으로 보호 제외, 원천 오류, 콘텐츠 오류를 구분했습니다. 별도 가상 입력 8행 중 대상 발송 7행을 분류한 결과는 보호 유지 4건, 원천·콘텐츠·사람 확인 각 1건, 자동 재발송 0건이었습니다. 실제 계정 발송 결과가 아닙니다.

Not Sent 추출 안내 ↗
추출한 자료는 어떻게 보관하도록 제안했나요?

장기 조회가 필요하면 Audit Trail의 계정별 보관 기간을 확인하고 정기 추출과 외부 보관을 계획합니다. SFTP도 영구 보관소로 보지 않고, 파일 건수·자동화 실패 알림·시간대·조회 권한을 함께 확인합니다. 실제 적용 시 최신 정책과 계정 조건을 재확인해야 합니다.

Audit Trail 공식 안내 ↗
삭제 후보와 관측 기간은 어떻게 검토했나요?

Contact Key 통일, 보호 대상 제외, 삭제 후보를 나누는 2단계 SQL 초안을 썼습니다. 재검토에서는 최근 7일 기록과 365일 비활동 비교의 기간 불일치를 바로잡았습니다. Data View의 관측 범위가 1년보다 짧으면 보관 이력·원천 재동기화를 대조한 뒤 승인받도록 했습니다.
