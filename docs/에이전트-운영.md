# 공통 에이전트 규칙과 스킬 번들 운영

확인일: 2026-11-16

## 문제 정의

공통 규칙은 Codex와 Claude Code 중심으로 작성되어 있었습니다. Hermes의 메모리와 스킬 번들, 실제 연동 확인 기준이 빠졌고, 회사별 `design.md`를 만드는 절차만 있었으며 별도 디자인 파일은 없었습니다. ELI5의 HTML 제작 방식까지 모든 답변의 기본값으로 삼으면 간단한 질문도 과하게 길어질 수 있습니다.

원본은 [AGENTS.md](../AGENTS.md)입니다. 이 저장소는 규칙과 설정의 배포 원본이며, GitHub 파일 수정만으로 다른 컴퓨터나 모든 에이전트의 설정이 자동으로 바뀌지는 않습니다.

## 문제 해결

### 공통 규칙과 작업 절차를 나눕니다

- AGENTS.md에는 한국어 응답, 사실 보존, 승인 범위와 완료 기준을 둡니다.
- 반복해서 함께 읽는 스킬은 네이티브 Hermes 번들로 묶습니다. 번들은 새 기능 구현이나 API 인증이 아니라, 설치된 스킬을 함께 읽게 하는 설정입니다.
- 프로젝트별 색과 폰트, 레이아웃 결정은 DESIGN.md에 둡니다.
- 마감과 제출 상태, 실제 지원 자료는 비공개 프로젝트 기록에 둡니다. 다른 도구의 메모리 경로를 Hermes 공통 경로처럼 사용하지 않습니다.

### 만든 번들

| 명령 | 언제 쓰는지 | 스킬 |
|---|---|---|
| `/jh-explain` | 처음 배우는 개념을 쉽게 설명할 때 | eli5, grounded-citations |
| `/jh-design` | 프로젝트 디자인 기준서와 시안을 만들 때 | design-md, claude-design |
| `/jh-apply` | 지원 서류를 작성하고 PDF와 Office 파일을 검수할 때 | humanizer, microsoft-office, pdf |
| `/jh-build` | 기능 구현과 테스트, 웹 사용 흐름을 검수할 때 | test-driven-development, requesting-code-review, dogfood |
| `/jh-travel` | 항공과 호텔 후보의 가격과 조건을 비교할 때 | travel-planning, maps |

예시:

```text
/jh-explain RLS가 내 데이터만 보여주는 원리를 텍스트로 설명해 주세요.
/jh-design 이 회사 지원용 포트폴리오의 브랜드 키트와 기준서를 만들어 주세요.
/jh-apply 이 채용 공고에 맞춰 마스터 이력서와 별도의 맞춤본을 만들어 주세요.
/jh-build 저장 실패 시 입력이 사라지지 않도록 테스트부터 추가해 주세요.
/jh-travel 날짜와 인원에 맞춰 왕복 항공과 호텔을 비교하고 후보 링크를 저장해 주세요.
```

ELI5는 큰 그림과 짧은 설명의 HTML을 기본으로 하는 스킬입니다. 번들의 instruction은 현재 요청의 출력 형식과 설명 깊이를 우선하도록 정했습니다. 텍스트 질문을 받았는데 매번 HTML을 만들지는 않습니다.

### 디자인 파일과 스킬의 관계

첨부된 설치 안내의 대상은 공식 `design-md` 스킬입니다. 별도 기능을 가정해 `hermes-design`이라는 스킬 이름으로 바꾸지 않았습니다.

- `design-md`: DESIGN.md의 구조화한 디자인 값, 참조, 색 대비를 작성하고 검사합니다.
- `claude-design`: 사용 흐름, 화면 구성과 시안 제작 절차를 제공합니다.
- `jh-design`: 위 두 스킬을 함께 읽게 하는 사용자 번들입니다.
- [DESIGN.md](../DESIGN.md): 개인 설명 자료용 제안 기본값입니다. 기존 이력서와 PDF에서 추출한 스타일이나 회사의 공식 브랜드가 아닙니다.
- [design/tokens.json](../design/tokens.json): DESIGN.md에서 실제 CLI로 내보낸 W3C DTCG 디자인 값입니다. 원본을 고친 뒤 다시 생성하며 수동으로 별도 수정하지 않습니다.

회사별 자료에는 조사한 `brand-kit.html`과 해당 지원 폴더의 `brand/DESIGN.md`를 우선합니다. 기존 소문자 `design.md`가 있으면 먼저 내용을 읽고 보존합니다. Windows에서 대소문자만 다른 두 파일을 만들지 않습니다. `desing.md`는 별도 표준으로 도입하지 않습니다.

### 확인 후 고친 공통 규칙

| 기존 항목 | 반영한 내용 | 이유 |
|---|---|---|
| Codex와 Claude Code만 안내 | Hermes의 프로젝트 규칙, 프로필 메모리와 번들 안내 추가 | 도구마다 실제 읽는 경로와 범위가 다릅니다. |
| 과거 메모리가 프로젝트 규칙보다 우선 | 현재 지시와 프로젝트 규칙, 도구의 보안 경계를 먼저 적용 | 오래된 기록이 현재 상태를 덮어쓰지 않게 합니다. |
| 고정된 네 줄 진행 안내 | 여러 단계 작업은 짧게 안내하고 실습 설명이 필요할 때만 확장 | 실행 전 결과를 쓰거나 같은 동작을 반복 설명하지 않게 합니다. |
| 승인받은 규칙 수정도 다시 질문 | 정확한 대상과 변경 범위를 이미 승인받았으면 진행 | 범위가 바뀌면 다시 확인하는 원칙은 유지합니다. |
| 공식 다운로드와 사용자 수치만 허용 | 실제 API와 도구 응답도 출처와 조회 시각을 붙여 사용 | 실시간 여행 가격과 설치 상태도 실제 조회 결과로 다룹니다. |
| 모든 도구가 Codex 메모리 경로 사용 | 도구별 저장소를 구분하고 임의 동기화를 금지 | Hermes의 다른 프로필까지 바꾸지 않습니다. |
| 파일 변경마다 새 이름 요구 | 제출본은 버전 보존, 지정한 코드와 문서는 최소 수정과 Git 이력 보존 | 승인된 문서 수정과 제출본 생성의 목적을 구분합니다. |
| 연동이 됐다는 단일 상태 | 설치, 발견, 인증, 프로젝트 연결, 요청 성공과 배포를 구분 | 테스트 응답이나 키 존재만으로 실제 AI 성공을 주장하지 않습니다. |

지원서 제출, 영상 공개와 이메일 발송을 사용자가 한다는 원칙, 회사 로고 미사용, 모든 쪽 이미지 검수와 사실을 부풀리지 않는 기준은 유지했습니다. 작업과 관계없는 이력서, 포트폴리오 PDF와 프로필 README는 바꾸지 않았습니다.

## 다른 환경에서 적용

설정 원본은 [skill-bundles/](../skill-bundles/)입니다. 번들이 참조하는 스킬을 먼저 설치해야 합니다. 현재 컴퓨터에서 확인한 설치 결과를 다른 프로필이나 WSL의 상태로 간주하지 않습니다.

Hermes의 현재 공식 문서는 번들을 `<HERMES_HOME>/skill-bundles/`에서 읽습니다. 실제 경로는 `hermes bundles list`로 확인합니다. 대상 프로필을 확인하고 같은 이름의 기존 파일과 비교한 뒤 필요한 YAML만 복사합니다. 예시의 `HERMES_HOME`은 실제 경로로 바꿉니다.

```bash
hermes bundles list
hermes bundles show jh-design
hermes bundles reload
```

빈 환경에서는 다음과 같이 만들 수도 있습니다. 기존 번들을 바꾸려면 먼저 내용을 비교하고 별도 승인된 범위에서 수정합니다.

```bash
hermes bundles create jh-design --skill design-md --skill claude-design --description "디자인 기준서와 실제 시안 제작"
```

이 명령은 스킬 목록만 묶습니다. 이 저장소 YAML의 추가 instruction까지 동일하게 적용하려면 YAML 원본도 함께 확인합니다. 번들 설치는 공통 AGENTS.md를 전역으로 주입하는 기능이 아닙니다.

공식 디자인 스킬 설치 명령은 다음과 같습니다. 이미 설치된 환경에서는 중복 실행할 필요가 없습니다.

```bash
hermes skills inspect official/creative/design-md
hermes skills install official/creative/design-md
```

디자인 검사와 내보내기는 실제 확인한 `@google/design.md@0.4.0`에 고정했습니다. Windows의 `.md` 실행 파일 연결 문제를 피하기 위해 `designmd` 별칭을 사용합니다.

```bash
npx -y -p @google/design.md@0.4.0 designmd lint DESIGN.md
npx -y -p @google/design.md@0.4.0 designmd export --format dtcg DESIGN.md
```

내보내기 명령의 JSON 결과를 `design/tokens.json`에 저장합니다. 검사 도구 업그레이드 때는 규격과 내보내기 형식을 재확인합니다.

## 결과 검토

### 확인한 것

- 변경 전 원격 main과 AGENTS.md 원문, 전체 파일 트리를 읽었습니다. 별도 DESIGN.md와 design.md, desing.md는 없었습니다.
- 공식 `design-md`를 현재 Hermes default 프로필에 설치하고 skill_view로 내용을 읽었습니다.
- 네이티브 CLI로 다섯 번들을 생성하고 list, show와 reload로 읽히는지 확인했습니다.
- 현재 프로필의 활성 스킬 목록과 대조하여 12개 의존 스킬이 모두 있는지 확인했습니다.
- DESIGN.md는 CLI 0.4.0 검사에서 오류 0개, 경고 0개였습니다. 규격 요약 정보는 1개였습니다.
- DTCG 내보내기를 실제 실행해 design/tokens.json을 생성했습니다.
- 문서의 상대 링크, 번들 YAML과 중복 이름, 변경 파일 범위를 검사합니다. GitHub 반영 후에는 정확한 원격 파일 내용을 다시 읽어 반영 여부를 확인합니다.

### 사용 제한

- 토큰과 색 대비 검사는 실제 화면의 전체 접근성 검사를 대신하지 않습니다. 기존 PDF를 이번 팔레트로 재디자인하거나 모든 쪽을 다시 렌더링하지 않았습니다.
- 번들의 등록과 의존성은 확인했지만, 각 번들로 새로운 지원서나 여행표를 다시 만드는 전체 작업을 실행한 것은 아닙니다.
- 다른 컴퓨터, Codex와 Claude Code의 로컬 사본, WSL과 다른 Hermes 프로필은 변경하지 않았습니다. GitHub 원본과 현재 프로필의 번들만 다룹니다.
- DESIGN.md 규격은 alpha이므로 버전을 바꾸면 호환성을 다시 확인해야 합니다.

### 앞으로 추진

새 컴퓨터에 적용할 때는 설치할 프로필과 기존 파일을 비교한 뒤 원본을 복사합니다. 적용 완료 기준은 그 환경에서 번들 목록과 의존 스킬이 확인되고, 실제로 수행할 작업 하나의 출력과 검증 기록이 남는 것입니다. 회사별 자료를 만들 때는 개인 기본값을 복제하는 대신 공식 출처를 먼저 조사하고, 해당 회사 기준서와 실제 결과물을 함께 검사합니다.
